24시간이다. 규칙은 **충돌 안 나게, 배포 안 깨지게** 두 가지만 지키면 된다. 역할과 담당은 11/1 결정 시트로 정했다 ([05 결정 기록](05_결정_기록.md)).

## 2. 누가 무엇을 정하나

문서(CLAUDE.md, 01, 03, 05)는 팀 공통 틀만 정한다: 아이에게 무엇을 알리고 부모에게 무엇이 가는지, 저장·API 구조, 범위, 역할. 그 안의 구체적인 것은 담당이 정한다. 문서 속 말투·대사·JSON·화면 예시는 예시일 뿐이다.

| 담당 | 정하는 것 |
| --- | --- |
| 건준 | 코끼리 말투·대사·대화 흐름, 부모 질문을 언제 어떤 말로 묻는지, 답장 카드에 담을 범위, 코치 메모, 프롬프트, 응답 필드 이름, Bedrock 모델 |
| 성준·재모 | 화면 배치·동작·세부 디자인, 색·글꼴·공용 컴포넌트(도하와 같이), 저장 구조(Supabase 테이블), 예시 가족 데이터 내용, 정적 화면 모양 |
| 도하 | 코끼리 생김새·상태, 서비스·코끼리 이름, 가격 숫자, 발표 |
| 성준·재모 중 A | 코인 기준 숫자(최소 몇 번 주고받기, 하루 몇 번). 03 핵심 흐름에 적고, B의 store.ts가 그 숫자로 지킨다 |

- 정한 것이 다른 사람 일에 걸리면(예: 응답 필드 이름) `types.ts`나 03에 적고 팀 채널에 알린다
- 틀(CLAUDE.md 절대 규칙, 05 확정)과 부딪히면 혼자 바꾸지 말고 팀 채널에서 정한 뒤 05에 덧붙인다

## 4. 브랜치 · 커밋 · PR

- `main` = **항상 배포되는 상태.** Vercel이 main을 자동 배포한다
- 작업은 `이름/기능` 브랜치 → PR → 한 명이 훑어보고 머지 (예: `jaemo/kid-chat`)
- 커밋 메시지는 한국어 한 줄: `아이 대화 화면 선택지 버튼 추가`
- 머지 전에 `npm run build` 통과 확인 (빌드 깨지면 배포도 깨진다)
- `.env.local`, API 키, 원본 수집 데이터는 **절대 커밋 금지**

**매번 하는 순서**
```bash
git switch main && git pull          # 최신 main 받기
git switch -c 이름/기능               # 새 브랜치
# … 담당 폴더에서 작업 …
npm run build                        # 통과 확인
git add -A && git commit -m "아이 대화 화면 선택지 버튼 추가"
git push -u origin 이름/기능          # GitHub에서 PR 만들기 (템플릿 체크)
```
- 큰 PR 하나보다 30~60분마다 작은 PR. 충돌이 줄고 배포 주소에서 바로 확인할 수 있다
- 다른 사람 PR이 머지되면 내 브랜치에 받아 온다: `git pull origin main`
- 15분 넘게 막히면 팀 채널에 바로 말한다
